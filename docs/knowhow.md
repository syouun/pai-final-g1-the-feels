## 1. プロジェクト概要と全体パイプライン

### 1-1. 目的

人の踊ってみた動画（伊原六花さんによる TWICE「The Feels」、2分19秒、定点カメラ）から全身の動きを取り出し、人型ロボット **Unitree G1（29 自由度、約 1.3 m、33.3 kg）** に、物理シミュレーション（MuJoCo）の中で**転ばずに同じダンスを最後まで踊らせる**。全編を **1 つの方策（ニューラルネット）** で踊らせることを本番の目標にした。

### 1-2. パイプライン

```text
元動画（29.97fps）
  │ ffmpeg で 30fps ちょうどに変換（2-1）
  ▼
GVHMR：単眼動画 → 人の 3D 姿勢（SMPL-X、世界座標）           … ノートブック1（T4）
  │ hmr4d_results.pt（全編 4,196 フレームに 1 回だけ推定）
  ▼
GMR：人の姿勢 → G1 の関節角（リターゲット、IK）
  │ the_feels_full_raw.csv（加工前を保存。以降の加工はここからやり直せる）
  ▼
gvhmr_to_g1_csv.py：推定ミスの補間 → ゼロ位相フィルタ → 接地補正 → CSV・プレビュー動画
  │ the_feels_full.csv（BeyondMimic 形式：根の位置3＋クォータニオン4(xyzw)＋関節29＝36列）
```

## 2. お手本データの生成・補正（データエンジニアリング）

### 2-1. フレームレートの罠：29.97fps と 30fps

- **問題【確認済み】**：GMR は GVHMR の結果を **30fps と決め打ち**で読む。元動画は 29.97fps なので、1 フレームあたり 1/1000 ずつ時間がずれる。
- **ずれの大きさ**：139.9 秒 × (30 − 29.97) / 30 ≒ **0.14 秒**。最後にはダンスが音より約 4 フレーム先に進む。20 秒の切り出しでは 0.02 秒しかずれないので、短いテストでは気づけない。
- **対策【実測】**：推定の前に ffmpeg で 30fps ちょうどに変換した（`-vf fps=30`）。結果は `r_frame_rate=30/1, nb_frames=4196, duration=139.92s`。
- **教訓**：複数のツールで時間軸をつなぐときは、各ツールの fps の解釈をソースで確かめる。誤差は長さに比例して効いてくる。

### 2-2. 全編に 1 回だけ推定し、部分はそこから切り出す

- 20 秒版（サビ後半）は、全編の `_raw.csv` から `--start 59.815 --end 80.78` で切り出した。区間は音声の相互相関で特定した（相関 0.996）【実測】。
- 部分と全体で入力をそろえておくと、20 秒版で確かめた設定と結果をそのまま全編に持ち込める。

### 2-3. 推定ミスの補間とゼロ位相フィルタ

- 推定ミス（1〜数フレームの姿勢の飛び）を、前後の中間からの外れ（根の位置 0.05 m、向き 30°、関節 0.8 rad）で検出し、補間した。全編で 12 フレーム（0.5〜0.6 秒、32.3〜32.6 秒、96.1〜96.2 秒）【実測】。
- 平滑化はゼロ位相の Butterworth（関節 7Hz、根の水平 4Hz、根の高さ 4Hz、向き 5Hz）。前向きと後ろ向きに 2 回かけるので時間の遅れがなく、音ハメが崩れない。
- 移動平均（窓 5）との比較（20 秒版）では、空中で止まる不自然なフレーム（hover）が 466 → 315 に減った一方、slip が 0 → 9 に増えた【実測】。**平滑化は「物理的な自然さ」と「動きのキレ」のトレードオフ**。

### 2-4. 接地補正（`--contact_h`）：終盤 30 秒の「浮き」の発見と解決

#### 現象【実測】

全編の方策（`model_19999`）は転ばずに完走したのに、位置誤差が**終盤だけ極端に大きかった**。

| 区間 | 位置誤差（平均） | 関節誤差（平均） | お手本で低いほうの足の高さ（中央値） |
|---|---|---|---|
| 0〜110 秒 | 7.0 cm | 0.168 rad | 3.4 cm |
| 110〜140 秒 | **17.9 cm**（最大 22.7 cm） | **0.147 rad**（むしろ小さい） | **20.5 cm** |

#### 原因の絞り込み（思考の流れ）

1. **関節は合っているのに位置だけずれる** → 姿勢の真似は正しく、「全身が一律にずれている」可能性。
2. **一律のずれの向き**：位置誤差の基準（`body_pos_relative_w`）は、水平はロボットの胴体に合わせ直すが、**高さはお手本の値をそのまま使う**【確認済み】。一律のずれが残るなら高さ方向。
3. **お手本の腰の高さを確認**：立っているときの腰は 0〜110 秒で約 0.77〜0.80 m なのに、110 秒以降は 0.97〜1.00 m【実測】。お手本が約 20 cm **宙に浮いている**。
4. **相関で裏づけ**：位置誤差とお手本の足の高さの相関係数は **r = 0.92**（110 秒より前だけでも 0.68）【実測】。
5. **学習側の兆候**：適応サンプリングが最も重点的に練習していた区間は約 128〜131 秒目に張り付いていた。手足の高さのずれ（`ee_body_pos`）による打ち切りも 1 反復あたり約 0.6 回で、20 秒版（約 0.1 回）の約 5 倍だった【実測】。ロボットは床に立つしかないので、宙に浮いたお手本は**永遠に追いつけない目標**になっていた。
6. **比較動画のコマ**：122 秒・128 秒で、右画面の緑のお手本の頭がロボットより高く、中央の画面では影が足から離れていた【実測：コマ画像】。

#### なぜ補正が効かなかったか【確認済み：`motion_filters.ground_offsets`】

接地補正は「低くて止まっている足」を接地とみなし、そのフレームで一番低い接地足が床に付くよう高さを補正する。接地とみなす条件が**足の高さ 3 cm 未満**（`contact_h=0.03`）かつ水平速度 0.4 m/s 未満だった。
人の 3D 推定（GVHMR）の高さのドリフトで全身が 20 cm 浮くと、**接地が 1 フレームも検出されない**。補正量は最後に接地した時刻（約 110 秒）の値を、終わりまでそのまま延ばしただけになっていた。

#### 解決（ノートブック3）

- `--contact_h 0.25`（25 cm）に広げて作り直した。速度の条件（0.4 m/s 未満）はそのまま。
- **関節角と根の水平位置は 1 ビットも変わらず**（最大差 1e-6）、**根の高さだけ**が変わった【実測】。

| 区間 | 高さの補正量（平均） |
|---|---|
| 0〜70 秒 | −0.1〜−4.7 cm |
| 70〜100 秒 | −6.4〜−9.2 cm |
| 100〜110 秒 | −4.6 cm |
| 110〜120 秒 | −15.3 cm |
| 120〜140 秒 | −20.6〜−21.4 cm |

| 物理チェック | 旧（`contact_h 0.03`） | 新（`0.25`） |
|---|---|---|
| hover（浮いたまま上向きの力が必要） | 2,842 / 4,196 | **70** |
| 足が浮いている割合 | 0.681 | **0.018** |
| 接地補正で接地とみなしたフレームの割合 | 0.21 | 0.87 |
| 補正後に接地している割合（足 3cm 未満かつ静止） | 0.34 | 0.93 |
| slip（滑り） | 53 | 145 |
| 接地中の足滑り 平均 | 0.123 m/s | 0.167 m/s |
| 補正量の範囲 | −0.030〜+0.040 m | **−0.249**〜+0.040 m |

#### 「ジャンプを潰していないか」の検証【実測＋解釈】

- 補正量は約 1Hz の低域通過をかけてから足すので、**速い上下動は残る**。腰の高さの細かい揺れ（1 秒の移動平均からのずれ）の標準偏差は、旧 3.23 cm、新 3.08 cm でほぼ同じ。
- 縮んだのは「両足が 0.5〜1.4 秒も床から 5〜8 cm 浮いたまま」の区間（例：17.7 秒は 8.1 → 2.9 cm）。0.5 秒以上空中にいるなら最高点は約 30 cm になるはずで（自由落下：h = g t² / 8、t = 0.5 秒で約 0.31 m）、5〜8 cm で浮き続けることは物理的に起こらない。人の 3D 推定の誤差と判断した【解釈】。
- 0.2 秒程度の短い跳ねは残った（128.1 秒：4.6 → 4.1 cm）。

#### 「滑りが増えた」の読み方【解釈】

slip と足滑りの増加は悪化ではない。接地とみなす時間が 34% → 93% に増え、旧お手本では浮いていたせいで数えられていなかった足のぶれ（推定誤差）が、**接地中の滑り**として見えるようになった。物理の G1 は足を踏ん張って止めるので、転倒の原因にはならない（摩擦 0.5〜1.0 すべて完走）。

#### 教訓

- **しきい値を使う検出は、データ全体が想定の範囲からずれると何も検出しない。** 「検出 0 件」と「問題なし」は違う。補正量が区間の端の値のまま延びていないかを確かめる。
- 位置誤差が大きいとき、まず「関節誤差も大きいか」を見る。**関節は合っていて位置だけずれる＝お手本の基準（高さ）がずれている**というパターンを疑える。
- 学習の重点区間（`sampling_top1_bin`）は、お手本の欠陥を指す。

### 2-5. 物理的に無理な箇所：10〜12 秒の深いしゃがみ

追加学習（3 章）の後も、最も誤差が大きいのはここだった【実測】。

| 指標（10〜12 秒） | 値 |
|---|---|
| 位置誤差（1 秒平均の最大） | 12.9 cm（11 秒） |
| 関節誤差（1 秒平均の最大） | 0.331 rad（11 秒） |
| お手本の腰の高さ（最低） | **0.38 m**（全編の中央値 0.77 m） |
| 横方向に必要な力 | 最大で体重の 0.97 倍 |
| 自己干渉のめり込み | 最大 **6.1 cm**（12〜13 秒） |
| 膝の曲げ | 最大 **2.75 rad（約 157°）** |
| 履歴 | model_4000 が 12.38 秒で転倒した場所（物理チェックの予想どおり） |

- 人は片膝が床に付くほど深くしゃがむが、体格（人 1.62 m、G1 約 1.3 m）と関節の可動域の違いで、G1 では中腰に近い不自然な姿勢になる【実測：コマ画像】。
- 全編の自己干渉の組の上位は、すべて手首がらみ：手首どうし（456 フレーム）、手首と股関節（66・60）、手首と胴（43）【実測】。手を合わせる・腰に手を当てる振付が、G1 では関節のめり込みになる。

**対応方針（ノートブック4、`edit_reference.py`）【未検証】**

| 手順 | 中身 |
|---|---|
| しゃがみを浅く | 脚の曲げ（股関節の前後・膝・足首の前後）を、区間の直前 2 秒の立ち姿勢の角度へ近づける：q' = q_立ち + (1 − (1 − k) · w(t)) · (q − q_立ち)。k = `depth_keep`（既定 0.6 ＝ 4 割浅く）、w(t) は区間で 1、前後 0.5 秒で余弦状に 0 |
| 腰の高さ | 脚を伸ばすと体が沈むので、低いほうの足と床の距離が元と同じになるよう根の高さを上げる（3Hz で平滑化） |
| 腕のめり込み | めり込むフレームで、その腕の肩の横開き（`shoulder_roll`）を、めり込みが 5 mm 以下になる最小量だけ外へ開く。開く向きは区間全体でめり込みが減るほうを自動で選び、前後 0.2 秒の最大値で広げてから 2Hz で平滑化（震え防止） |
| 区間の外 | **1 フレームも変えない**（代役のモジュールで確認済み） |

- 判定には **mjlab の G1（腕の当たり判定がある版）** を使う。GMR の G1 は腕のジオムが見た目用で、当たり判定がない【確認済み：xml】。
- MuJoCo が手元で使えなかったため、MuJoCo と scipy の代役を作って処理の流れだけ確かめた。実際の数値は Colab で出る（下の「結果」）。

#### 結果（ノートブック4、`depth_keep 0.6`、区間 9.5〜13.5 秒、前後 0.5 秒でつなぐ）【実測：`_edit_report.json`】

| 指標 | 補正前（`g25`） | 補正後（`g25s`） |
|---|---|---|
| 腰の最低の高さ | 0.385 m | **0.59 m** |
| 根の高さを上げた量（最大） | — | 21.4 cm |
| 脚の関節の変化（最大） | — | 0.875 rad |
| 足と床の距離の変化（最大） | — | 0.9 cm（足の着き方はほぼ変わらない） |
| 自己干渉のめり込み（最大） | 6.7 cm | **3.8 cm** |
| めり込みが許容（5 mm）を超えたフレーム | 39 | 11 |
| 肩を外へ開いた量（最大） | — | 左 0.63 / 右 0.62 rad |

- めり込みは減ったが、**目標の 5 mm 以下には届かなかった**（最大 3.8 cm、11 フレーム）。残りは手首どうし・手首と胴の組。
- 区間（9〜14 秒）の誤差【実測、摩擦 0.8】：

| 条件 | 関節誤差 | 位置誤差 | 最大位置誤差 |
|---|---|---|---|
| ③ NB3 方策 × 元のお手本（`g25`） | 0.1987 rad | 7.97 cm | 16.78 cm |

|---|---|---|---|---|
| ③ → ③' | お手本だけ | −16% | −23% | −43% |

報酬の形は exp(−誤差² / std²)。std を小さくすると、同じ誤差でも報酬が下がり、**細かいずれを直す勾配が強くなる**。関節角そのものの報酬はなく、関節は体の位置・向きの報酬を通して間接的に合わせている。

### 3-3. 実行時間：「6 時間以上」→「3 時間未満」の正体

**結論：時間の差は、ほぼ反復回数の差だけ。** 転倒の頻度や初期の探索は、1 反復の時間にほとんど影響しない。

| 区間 | 1 反復の時間 | うち経験の収集 | うち学習（勾配計算） | 平均エピソード長 |
|---|---|---|---|---|
| 全編スクラッチ 0〜200 反復（転倒だらけ） | 1.54 秒 | 1.41 秒 | 0.134 秒 | 8 ステップ |
| 全編スクラッチ 19,500〜20,000 反復 | 1.64 秒 | 1.51 秒 | 0.131 秒 | 471 ステップ |
| 追加学習 全体 | 1.60〜1.62 秒 | 1.47〜1.49 秒 | 0.131 秒 | 434 → 493 |

**1 反復の時間がほぼ一定の理由【確認済み：構造】**

- 1 反復では、4,096 体のロボットを GPU 上で同時に **必ず 24 ステップ**動かす（合計 98,304 ステップ）。転んだロボットは、その場でお手本の別の時刻からやり直す（リセット）だけで、計算の量は減らない。
- リセットも GPU 上でまとめて行うので、転倒が多くても時間はほとんど増えない。むしろ転倒だらけの初期（1.54 秒）のほうが少し速い。床との接触が少ない姿勢では接触計算が軽くなるためと考えられる【解釈】。
- 学習（勾配計算）は 1 反復あたり約 0.13 秒で一定。ネットワークの大きさとミニバッチの数で決まり、方策の上手さに関係しない。

**所要時間の内訳**

| | スクラッチ（NB2） | 追加学習（NB3） |
|---|---|---|
| 反復回数 | 20,000 | 4,000 |
| 学習時間 | 20,000 × 約 1.63 秒 ≒ **9 時間 5 分** | 4,000 × 約 1.61 秒 ≒ **1 時間 47 分** |
| それ以外 | インストール、変換、評価、動画 | インストール 5〜10 分、お手本の作り直し・物理チェック・npz 変換 約 10 分、評価（6 本）・比較動画 約 30〜40 分 |
| CU の目安（A100 ≒ 13 CU/時） | 約 120 | 学習 約 23、全体 約 35〜40 |

チェックポイントの読み込みの効果は「1 反復を速くする」ことではなく、**必要な反復回数を減らす**ことに表れる。

### 3-4. 追加学習が成功したメカニズム

#### チェックポイントから引き継がれるもの【確認済み：rsl_rl の保存形式と mjlab の `runner.load`】

| 要素 | 役割 |
|---|---|
| 方策（actor）の重み | 観測 → 行動。「どう踊るか」の本体 |
| 価値関数（critic）の重み | 状態の良さの見積り。PPO の学習信号（アドバンテージ）の基準 |
| 観測の正規化の統計（平均・分散） | 入力のスケールをそろえる |
| 行動のばらつき（探索の幅、std） | 学習の進みに合わせて縮んでいく |
| Adam の内部状態（勾配の移動平均） | 学習率の実質的な大きさ |
| 反復の番号 | 19,999 から数え続ける（ログは 19,999〜23,998） |

引き継がないもの：適応サンプリングの区間ごとの失敗の記録（環境の側にあるので、毎回ゼロから）。

#### 学習の推移【実測】

| 反復（追加学習） | 平均エピソード長 | ee_body_pos 終了 | 学習中の位置誤差 | 関節誤差の指標 | 行動の std | 重点区間 |
|---|---|---|---|---|---|---|
| 19,999〜20,199 | **434** | **5.48** | 0.086 | 1.369 | 0.298 | 約 12 秒 |
| 20,199〜20,999 | 481 | 0.23 | 0.052 | 0.903 | 0.270 | 約 66 秒 |
| 20,999〜22,999 | 490 | 0.14 | 0.045 | 0.763 | 0.259 | 約 66 秒 |
| 23,498〜23,999 | **493** | **0.12** | **0.039** | **0.674** | **0.250** | 約 66 秒 |
| （参考）スクラッチの最後 500 反復 | 471 | 0.61 | 0.168 | 1.028 | 0.300 | 約 131 秒 |

**読み取れること【解釈】**

- **最初の 200 反復の落ち込み**：エピソード長が 471 → 434 に下がり、手足の高さによる打ち切りが約 9 倍に増えた。原因は 2 つ。
  1. 報酬の式を変えた（許容幅を締めた）ので、価値関数の見積りが古い式のまま。アドバンテージがずれ、方策が一時的に揺れた。
  2. 学習中は外乱と摩擦のばらつきがあり、新しいお手本の高さの変化に方策がまだ合っていない。
- **数百反復で回復**：価値関数は回帰の問題なので、方策より速く新しい報酬に追いつく。1,000 反復後には、スクラッチの最後を上回った。
- **探索の幅の縮小（0.30 → 0.25）**：許容幅を締めて「正確さ」の勾配が強くなり、方策がより決定的になった。

#### なぜ少ない反復で効くのか

- バランスの取り方と振付の大部分は、すでに重みに入っている。変わったのは「お手本の高さ（一部の区間）」と「報酬の細部」だけで、**最適解が近くにある**。
- スクラッチの序盤（立てない → 転ばない）の約 6,000 反復分を丸ごと飛ばせる。

#### メリットと注意点

| | 内容 |
|---|---|
| メリット | 計算が約 1/5。すでに完走できる状態から始めるので、学習が崩れにくい |
| 壊滅的忘却 | 別の振付で追加学習すると元の振付を忘れることがある。今回は同じ振付で高さだけ変わったので心配は小さい |
| 過学習 | 1 つのお手本の模倣では評価も同じお手本なので、通常の意味の過学習は起きにくい。代わりに**頑健性**（摩擦・外乱）が落ちないかを見る → 摩擦 3 条件で維持を確認 |
| 探索の幅の縮小 | 続けすぎると今のやり方に固まり、改善が止まる（局所解）。std の推移を見張る |
| 報酬の変更 | 最初の数百反復は一時的に悪化する。**途中のチェックポイントを早まって評価しない** |
| 交絡 | お手本・報酬・反復回数を同時に変えたので、効果を分けるには対照実験が要る（6-2） |

### 3-5. 報酬のチューニング方針

| 項目 | 既定 | NB3 | NB4 | ねらい |
|---|---|---|---|---|
| `action_rate_l2` の重み | −0.1 | **−0.05** | −0.05 | 動きの変化への罰則を半分に → 鋭さ |
| `motion_body_pos` の std | 0.3 m | **0.25** | 0.25 | 体の位置の細かいずれ |
| `motion_body_ori` の std | 0.4 rad | **0.3** | 0.3 | 腕・脚の向き（≒関節） |
| `motion_global_root_pos` の std | 0.3 m | 0.3 | **0.2** | 立ち位置のずれ（ドリフト） |

- 変更は `train_sim.py` の引数（`--action-rate-weight`、`--body-pos-std`、`--body-ori-std`、`--root-pos-std`）で行い、ログ先頭の `[train_sim]` 行に実際の値を出す。
- **震えの検証指標**として、`render_policy.py` に `mean_action_rate`（0.02 秒ごとの方策の出力の変化の平均）と `p95_action_rate` を追加した。目安は「元の方策より 3 割以上増えたら震えを疑い、`−0.075` に戻す」。
- 結果【実測】：変化量は 0.1029 → 0.1093（+6%）、95 パーセンタイルは 0.2054 → 0.2228（+8%）。罰則を半分にしたわりに増え方は小さく、震えの兆候はない。
- **許容幅を締めるのは追加学習のときだけ**。最初から締めると、報酬がほぼ 0 の状態が続いて学習が進みにくい（最初は広く、上手になったら狭く＝カリキュラムの考え方）。
- 一度に変えるのは 1〜2 項目まで。NB4 では立ち位置の許容幅だけを足し、ほかは NB3 から引き継ぐ。
- NB4 の結果【実測】：行動の変化量は 0.1097（NB3 方策）→ 0.1090。立ち位置の許容幅を締めても震えは増えていない。

### 4-6. 評価の落とし穴：「0.02 秒で転倒」（10/17 に解決）

**現象【実測】**：20 秒版の `model_4999`（学習ではエピソード長 500）を評価すると、摩擦 0.5 / 0.8 / 1.0 の 3 条件とも 1 ステップ目（0.02 秒）に `ee_body_pos` で止まった。誤差がすべて 0.0 なのは、1 行も記録されないままループを抜けたため（記録は転倒判定の後）。

**手がかりと推理**

1. **学習と評価が食い違う**：学習の最後の数百反復では、手足の高さによる終了は 1 試行あたり 0.04 回。方策が本当に 1 ステップ目で倒れるなら学習中にも頻発するはず → **方策ではなく評価の手順を疑う**。
2. **条件を変えても結果が変わらない**：物理的な転倒なら摩擦で時刻が変わるはず。3 条件ともぴったり 0.02 秒 → **物理ではなく初期化の問題**。
3. **開始時のずれを 1 行で測る**：お手本 − ロボットの胴体のずれは x・y・z とも 0.000 m【実測】。「区間の切り出しで初期位置がずれている」という仮説はこれで否定 → ずれていないのに「ずれている」と言う → **判定に使う値のほうがおかしい**。
4. **終了条件を外すと最後まで踊れる**：20.94 秒を完走し、位置誤差は平均 7.5 cm・最大 16.6 cm で、しきい値 0.25 m を一度も超えない → **方策は正常で、判定の入力がおかしい**。

| 仮説 | 予想される現象 | 判定 |
|---|---|---|
| A. 方策が本当に転ぶ | 学習中も頻発、摩擦で時刻が変わる | 棄却（1・2・4） |
| B. 切り出しで、お手本の初期位置が原点からずれている | 位置のずれで判定に当たる | 棄却：判定は胴体の水平位置に合わせ直した値で、しかも高さだけを見る。開始時のずれも 0（3） |
| C. 評価用の設定（摩擦の固定、ランダム化の除去）が悪さをしている | 設定を戻すと直る | 2 と矛盾。可能性は低い |
| D. 比較用の値がリセット直後に未計算 | 1 ステップ目だけ誤判定、条件によらない | **採用**（ソースで確定） |

**ソースでの確定【確認済み：mjlab v1.2.0、unitree_rl_mjlab `1425b15`】**：`ee_body_pos`（`bad_motion_body_pos_z_only`）は、`command.body_pos_relative_w`（お手本の手足の位置を胴体基準に直したもの）の**高さ**とロボットの手足の高さを比べる。この値は 0 で初期化され、`_update_command()` でだけ計算される。`env.reset()` はこれを呼ばず、`env.step()` の中の順番は「物理計算 → **終了判定** → 報酬 → リセット → **コマンドの更新** → 観測」。そのため reset 直後の最初の step では、お手本の手首の高さ 0 m とロボットの手首約 0.8 m を比べて「転倒」と判定する（足首は床に近いので引っかからず、手首だけが原因になることとも合う）。
- 学習で問題にならないのは、途中のリセットが step の中で行われ、同じ step のうちにコマンドが更新されるから。影響は学習開始直後の 1 ステップだけ。

**修正**（`render_policy.py`、10/17）：`env.reset()` の直後に `cmd.time_steps -= 1; cmd._update_command()`（お手本の先頭フレームのまま値だけ計算する）。修正後は 20 秒版が 3 条件すべて完走した（4-5）【実測】。

**評価の条件の固定（旧 E-02〜E-04）**：play モードでも残っていた起動時のランダム化（足裏摩擦・重心・関節センサーのずれ）を外して摩擦を固定し、誤差は学習の報酬と同じ胴体基準で測り、立ち位置のずれは別の項目に分け、最初の転倒で止めて時刻と条件を記録する。ただし **GPU の計算は毎回わずかに違うので、境界ぎりぎりの場面では同じ条件でも結果が変わる**（4-8b）。

**教訓**
- 学習ログと評価が食い違ったら、まず**評価側**を疑う。評価コードは自作で、テストされていない。
- **条件を変えても結果が変わらない**ことは強い手がかり（物理の問題なら条件で変わるはず、という逆からの推論）。
- 「終了条件あり／なし」の両方を用意しておけば、方策の問題か判定の問題かを 1 回で切り分けられる。
- もっともらしい仮説ほど、**直す前に 1 行の計測で確かめる**（開始時のずれの表示で仮説 B を否定し、間違った修正をせずに済んだ）。
- フレームワークの環境を「1 つだけ・リセット直後から」動かすと、学習中は隠れている初期化の順序の問題が表に出る。`reset` と `step` の中で何がどの順に計算されるかをソースで確かめる。

## 5. レンダリングとカメラ制御

### 5-1. MuJoCo のカメラの仕様【確認済み】

| パラメータ | 意味 |
|---|---|
| `azimuth`（水平角、度） | カメラが**向いている**水平方向。前向きのベクトルは (cos el · cos az, cos el · sin az, sin el) |
| `elevation`（仰角、度） | 負で見下ろす |
| `distance`（m） | 注視点からの距離。カメラ位置 = 注視点 − distance × 前向きベクトル |
| tracking カメラ | 指定した体（`torso_link` や `pelvis`）の**位置**についていく。**体の向きにはついて行かない**（見る方向はワールドに固定） |

例：azimuth 90° → +y 方向を向き、−y 側から撮る。azimuth 270° → −y 方向を向き、+y 側から撮る。

### 5-2. なぜ背面からの動画になっていたか

**お手本の体の向き【実測】**：根のクォータニオン（xyzw）から求めた水平の向き（yaw）の平均は **91.3°**（+y 方向を向いて踊っている）。G1 の正面は体の +x。

|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| yaw の平均 [°] | 144 | 91 | 70 | 78 | 88 | 115 | 107 | 88 | 80 | 106 | 82 | 102 | 89 | 32 |

### 5-3. 正面への変換

- **中央・右**：正面は踊り手の向きの反対側から撮ること。azimuth = 平均の yaw + 180° ≒ **271° → 270°**。
  - `render_policy.py --azimuth 270 --elevation -5 --distance 2.8`（`--elevation` は 10/18 に追加）
  - `gvhmr_to_g1_csv.py --cam_azimuth 270`（`--cam_elevation`、`--cam_distance` とともに 10/18 に追加。既定は従来どおり 90 / −10 / 3.0）
  - プレビューだけ作り直すときは、`--from_csv <お手本.csv> --ground none --no_outlier --filter none --cam_azimuth 270` で**データを素通し**させ、別のフォルダに出力する（お手本そのものは変えない）。
- **左**：`render_gvhmr_front.py`（10/18 新規）【未検証】。保存済みの `hmr4d_results.pt` から、`demo.py` の `render_global` と同じ処理（メッシュ、床、照明、24mm レンズ）で描き、**カメラの置き場所だけ**を「全フレームの体の向きの平均の正面」に変える。体の向きは GVHMR 自身の定義（腰と肩の左右から、左 × 上 ＝ 正面）で計算する。推定はやり直さないので、GVHMR のインストール（15〜25 分）＋描画（10〜20 分）で済み、T4 で動く。`--view_deg` で回り込み（0 = 正面、180 = 背面）、`--max_frames 90` で試し描きができる。
- **限界**：tracking カメラは体の向きについて行かない。体の向きが正面 ±45° に入るのは全体の **71%**【実測】。0〜10 秒（yaw ≒ 144°）と 130〜140 秒（≒ 32°）は斜めからの画になる。
- 左右反転で代用するのは不可。振付の左右が逆になる。

3. 出力名は `front_` で始める。評価や比較のセルが「最新の `policy_*.mp4`」を自動で拾うので、背面の動画と取り違えないため。

### 5-5. 動画まわりの注意

- `render_policy.py` は全フレームを RAM に貯めてから書き出す。全編（約 7,000 フレーム、1280×720）では約 19 GB → **ハイメモリが必要**。
- 大きい動画を `show()`（base64 でノートブックに埋め込む）で表示するとブラウザが固まることがある。ドライブから直接開く。

### 6-2. 最難所（10〜12 秒）への取り組み方

- 学習でどうにかするより、**お手本を直すほうが確実**。G1 の体で物理的に無理な姿勢は、何反復学習しても追従できない（終盤の浮きと同じ構図）。
- 直す強さは段階的に（`depth_keep` 0.75 → 0.6 → 0.5）。浅くしすぎると振付が変わる。補正の前後をプレビュー動画と物理チェックの表（腰の最低高さ、めり込み、横の力、滑り）で比べる。
- 区間の外は変えない（前後 0.5 秒で滑らかにつなぐ）。音ハメと他の区間の学習結果を守るため。

### 6-3. 立ち位置のずれ（ドリフト）の注意

- エピソードは 10 秒なので、方策は 140 秒の通しを一度も練習していない。ずれは少しずつ溜まる。①は 23.7 秒で最大 31 cm、③は 32.5 秒で最大 24 cm、終了時はどちらも約 3 cm【実測】。
- 根の位置の許容幅を締めると、体勢の追従と取り合いになる（立ち位置を戻すために足を余計に動かす）。**一度に締めるのは 0.3 → 0.2 まで**にし、関節誤差・位置誤差が悪化しないかを確認する。
- 誤差は胴体基準（ドリフトを除く）とドリフトを分けて記録する。混ぜると、どちらが悪いのか分からなくなる。

### 6-4. 追加学習の限界

- 行動の std は 0.30 → 0.25（NB3）→ 0.24（NB4）。続けるほど探索が減り、今のやり方に固まる。std が 0.2 を切る、または誤差が横ばいになったら止めどき。
- **精度を上げる追加学習は、頑健性を削ることがある**：NB4 は摩擦 0.8 の精度を上げたが、NB3 では完走していた摩擦 1.0 で止まった（4-8）。追加学習のたびに、精度だけでなく摩擦の試験も見る。
- 報酬の式を変えた直後の数百反復は一時的に悪化する。**最初の 500 反復のチェックポイントで判断しない**。
- 何度も追加学習を重ねると、「どの変更が効いたか」が分からなくなる。run 名に変更点を入れ（`_ft`、`_ft2`、`_abl`）、評価は**同じお手本の上で**比べる（お手本が変わると誤差の基準が変わるため）。

### 6-5. 計算リソースの配分

| 作業 | おすすめのランタイム | 理由 |
|---|---|---|
| 人の 3D 推定・メッシュの描き直し | T4（約 2 CU/時） | GPU をそれほど使わない。インストールが長いので安い GPU で |
| お手本の作成・物理チェック | CPU で可（T4 でも） | GMR と MuJoCo の逆動力学は CPU |
| 強化学習 | A100（約 13 CU/時） | 1 反復 1.6 秒。L4 は未測定（1 反復 4.5 秒より速ければ L4 のほうが安い） |
| 全編の評価動画 | A100 ハイメモリ（または解像度を下げる） | 約 19 GB の RAM |

- 実績【実測】：20 秒版 5,000 反復 2 時間 23 分、全編 20,000 反復 9 時間 5 分、追加学習 4,000 反復 1 時間 47 分。
- 反復数の見積り：「転ばない」までは 20 秒版で約 1,000、全編で約 6,000 反復。精度を磨く段階は、追加学習で 4,000 反復でも大きく効いた。**スクラッチは「転ばない＋そこそこの精度」で切り上げ、残りは修正したお手本で追加学習する**ほうが CU の効率が良い。
- 学習は `setsid nohup` で切り離し、監視セルが 10 分ごとにドライブへ同期する。切断しても失うのは最大 10 分。

### 6-6. 教訓のまとめ（Best Practices & Pitfalls）

1. **転ばないことと、正確に踊ることは別の段階**。エピソード長が上限に近づいても、誤差は下がり続ける。
2. **誤差の大きい区間は、まずお手本を疑う**。「関節は合っているのに位置だけずれる」はお手本の基準のずれのサイン。終盤の浮きは r = 0.92 で説明できた。
3. **しきい値の検出は、範囲外では何も起こさない**。「検出 0 件」を「問題なし」と読まない。
4. **適応サンプリングの重点区間は診断ツール**。128〜131 秒（お手本の欠陥）→ 66 秒（本来の難所）と、直すべき場所を指した。
5. **学習と評価が食い違ったら、評価側を疑う**（0.02 秒の誤判定）。
6. **比較は 1 つずつ変えて行う**。「旧方策 × 新お手本」の 1 行が、お手本の修正の効果（−42%）を切り出した。
7. **時間を決めるのは反復回数**。GPU 並列の強化学習では、1 反復の時間は上手さによらずほぼ一定。
8. **追加学習は、引き継ぐもの（重み・正規化・探索の幅・最適化の状態）と、引き継がないもの（適応サンプリングの記録）を意識する**。報酬を変えた直後の一時的な悪化は想定内。
9. **カメラは「どこから撮るか」ではなく「どちらを向くか」で指定する**（MuJoCo の azimuth）。正面は「平均の向き + 180°」。
10. **手元で動かせない処理は、代役で流れを確かめ、結果の数値は本番の環境で確かめる**。作成環境から PyPI に接続できず MuJoCo を入れられなかったため、補正スクリプトは代役のモジュールで流れだけ確認し、数値は Colab の物理チェックで確認する手順にした。
11. **スクリプトを直したら、ドライブ側に届いているかを確かめてから実行する**。ノートブックの冒頭で、修正版にしかない文字列を `grep` して、古い版なら止める。
12. **止まった時刻ではなく、崩れ始めた時刻を見る**。摩擦 1.0 の停止は 7.36 秒だったが、崩れ始めは 5.5 秒。正常に完走した条件と、時刻ごとの誤差・ドリフトを並べると分かる。
13. **決定論的な評価の 1 回の失敗（成功）は、境界の目安でしかない**。摩擦を少しずつ変える（0.9・1.0・1.1）と、崖なのか偶然なのかが分かる。
14. **重点練習区間は、ログの最後の 1 行ではなく分布で読む**。NB4 の最後の値は 32 秒だったが、最後の 500 反復では 104 秒が最多で、1 位の確率も NB3 の 3 分の 1 に下がっていた。
15. **お手本の補正とロボットの学習の効果は、同じお手本の上で 1 行ずつ分ける**。しゃがみでは、改善のおよそ半分ずつがお手本と学習だった（2-5）。
16. **「決定論的なはずの評価」も、GPU では繰り返すと結果が変わることがある**。境界の近くでは、1 回の結果で判断せず、同じ条件を数回評価して回数で比べる（4-8b）。
17. **転倒した瞬間の値は、自動リセットの後に読むと意味がない**。step の中で終了判定とリセットが両方起きるので、1 ステップ前の値を控えておく。
18. **Colab の `%%bash` セルで ffmpeg を呼ぶときは、標準入力を切る**（`-nostdin` か `< /dev/null`）。`%%bash` はセルの中身を標準入力から bash に渡すので、ffmpeg がキー操作の受付のために標準入力を読むと、セルの残りの行を飲み込む。症状は「`Enter command: <target>|all …`」「`Parse error`」、または行の途中から始まる謎の `command not found`（手順 5 の `-9s.mp4`、手順 8 の `ripts/make_comparison.sh`）。
19. **自動選定は 1 つの指標で選ばない**。関節誤差だけで選ぶと、評価の揺れの範囲の差（0.0003 rad）で、位置誤差・最大誤差・頑健性が劣る版を選んだ（4-8c）。採用前に、複数の指標と区間別の誤差を表で並べる。
20. **追加学習は「出発点より良くなったか」で判断する**。NB5 は条件を厳しくしたぶん探索が広がり、2,500 反復では出発点を超えなかった。続ける前に、出発点を比較対象に入れる。
21. **ライブラリの版は 2 段階で固定する**（リポジトリのコミットと pip の版）。下限だけ指定のライブラリは時間がたつと壊れる（7-4）。
22. **一括実行で危険なセルは、既定で何もしない**。失敗は次のセルに持ち越さない（8-1・8-2）。
23. **本番規模の前に、小さな学習で評価まで一周する**（9-5）。

| 並列環境 / 1 反復 | 4,096 環境 × 24 ステップ |
| 1 反復の時間 | 20 秒版 中央値 1.73 秒、全編 1.54〜1.64 秒（3-3）。最初の 1 回だけ GPU のカーネルのコンパイルで 4.4 秒 |
| 実績 | 20 秒版 5,000 反復 2 時間 23 分、全編 20,000 反復 9 時間 5 分、追加学習 4,000 / 3,000 / 2,500 反復 1 時間 47 分 / 1 時間 22 分 / 1 時間 8 分 |

- **L4 は最後まで未測定**。比べるときは「1 反復あたりの CU」＝ 1 反復の秒数 ÷ 3600 × CU/時。A100（約 13 CU/時）は 1.6 秒 × 13 ÷ 3600 ≒ **0.006 CU/反復**。L4（約 5 CU/時）が得になるのは、1 反復が約 4.2 秒より速いとき。
- 使い分け：長い学習は A100（全編 20,000 反復を L4 で 2.6 倍遅く回すと 24 時間の上限に当たる）。人の 3D 推定・お手本の作成は T4、物理チェックは CPU で動く。
- **教訓**：「速い GPU は高い」とは限らない。CU は時間 × 単価なので、1 反復あたりの CU で比べる。

### 7-2. 「A100 ハイメモリ」は何に効くのか（旧 H-02）

ハイメモリが増やすのは **CPU 側の RAM** で、GPU のメモリではない。

| 処理 | 主に使うメモリ | ハイメモリの効果 |
|---|---|---|
| 4,096 環境の物理計算・方策の学習 | GPU のメモリ（MuJoCo Warp・PyTorch） | 直接は効かない |
| **評価動画の書き出し** | **CPU の RAM** | **大きく効く** |
| ffmpeg（比較動画・提出動画） | CPU の RAM（少量） | ほぼ関係なし |

- `render_policy.py` は描画した全フレームを貯めてから書き出す。1 フレーム 1280×720×3 ≒ 2.76 MB なので、**全編（約 6,990 フレーム）で約 19 GB**、20 秒版で約 2.9 GB【確認済み：作り】。標準メモリでは落ちる。
- 対策：ハイメモリで書き出す（今回の運用）／`--width 960 --height 540` で約 56% に減らす／【未実装】1 枚ずつ書き出す形（`mediapy.VideoWriter`）に変える。
- 全編の動画は 1 本ずつ**順番に**書き出す（NB5 の手順 8）。終了条件なし・`--t-end 9` の短い動画は 1 本 2〜3 GB なので並列でよい。
- **教訓**：本当に CPU の RAM を食うのは「環境の数」ではなく、**長い動画を一度にメモリへ載せる処理**。

### 7-4. 版の固定：`mjENBL_MULTICCD` エラー（旧 T-10）

- **教訓**：リポジトリのコミットを固定しても、その先の pip の版は固定されない。**2 段階で固定**する。レポートの使用バージョンにも両方を書く。

## 8. ノートブックの運用：一括実行・同期・止まったとき

### 8-1. 一括実行（Run All）を安全にする（旧 R-01・R-02）

一括実行の危険は「エラーで止まること」ではなく、**エラーなく最後まで走ってしまうこと**。説明文に「切断されたときだけ実行」と書いても、一括実行は読まない。

| 危険なセル | 一括実行で起きること | 守り方（実装したもの） |
|---|---|---|
| 速度測定（NB2） | 本番前に 50 反復が毎回走る。測定用の run が「一番新しい run」として誤って拾われる | `RUN_SPEEDTEST = False` のスイッチ。既定は何もしない |
| 切断後の再開（NB2〜5） | 学習が終わった直後に、追加の学習が自動で始まる（NB2 では既定 10,000 反復 ≒ 4.8 時間・63 CU） | NB2 は `RESUME = False`、NB3〜5 は `REMAIN=0` のとき何もしない |
| 学習の開始（NB5） | 学習が済んだ状態で一括実行すると、2,500 反復の学習がもう一度始まる（約 1 時間・15 CU） | 同じ run 名にチェックポイントがあれば `[skip]`。監視セルも PID のファイルがなければ何もしない（10/19 追加） |
| 評価（NB5） | 同じ評価を何度もやり直す（1 本 約 6 分） | 結果の JSON がドライブにあれば計算し直さない。動画も、あれば作り直さない |

```python
RUN_SPEEDTEST = False   # 手動で測るときだけ True
RESUME = False          # 再開するときだけ True にして、そのセルを手動で実行
os.environ['RUN_SPEEDTEST'] = '1' if RUN_SPEEDTEST else '0'
os.environ['RESUME'] = '1' if RESUME else '0'
```

```bash
if [ "$RESUME" != "1" ]; then echo "[skip] 再開セルは実行しません（RESUME = False）"; exit 0; fi
```

- `exit 0` で抜けるのでセルは緑のまま。一括実行は止まらず、後ろの評価まで進む。スキップしたことは 1 行で表示する。
- **セルは前のセルの変数に頼らない**。グラフのセルが別のセルで読み込んだ `plt` に頼っていて、手順を飛ばすと `NameError` になった（NB5 手順 7）。使うものはそのセルで読み込む。

### 8-2. 学習の切り離し・二重起動の防止・終了時の成否チェック（旧 R-03・R-04）

```text
学習セル：setsid nohup で起動 → PID と予定反復数を /content/train.pid・train.iters に書いて、すぐ終わる
   │       ログは $P/logs/train_<NAME>.log（ドライブ）に直接追記
   ▼
監視セル：PID が生きている間ずっと回る（前面）
   ├ 60 秒ごと：ログから「反復・エピソード長・報酬・行動の std・ETA・エラー」の行だけ表示
   ├ 10 分ごと：ローカルの logs/rsl_rl をドライブへ同期（sync_logs.sh）
   └ 終了時：最後に同期 → 成否チェック（Traceback／チェックポイント 0 個／予定の 95% 未満なら例外で止める）
```

| 決めたこと | 理由 |
|---|---|
| 学習はバックグラウンド、監視は前面 | 監視セルだけ何度でもやり直せる |
| 起動時に PID が生きていれば `exit 1` | 同じ GPU で 2 つの学習が動くのを防ぐ。二重起動は後ろに進んではいけないので、ここは失敗で止める |
| チェックポイントはローカル、10 分ごとにドライブへ | ドライブへの直接書き込みは遅く不安定（TensorBoard は細かい書き込みが多い） |
| テキストのログだけはドライブに直接 | 追記だけで軽い。仮想マシンが消えても進み具合が残る |
| `PYTHONUNBUFFERED=1` | ないと Python の出力がバッファにたまり、ログへの反映が数分遅れる |
| 終了時の成否チェックで例外 | 学習が失敗したまま評価に進み、古いチェックポイントで意味のない評価をするのを防ぐ |
| 予定の 95% を基準 | 最後の反復番号は「予定 −1」（5,000 予定なら 4,999） |

**教訓**：ノートブックは「1 セルずつ見ながら」と「一括実行で放っておく」の両方で安全に作る。**危険なセルは既定で何もしない**、**失敗は次のセルに持ち越さない**。

### 8-3. `%%bash` のセルと ffmpeg（10/19）

- `%%bash` はセルの中身を**標準入力**から bash に渡す。ffmpeg はキー操作を受け付けるため標準入力を読むので、**セルの残りの行を飲み込んで止まる**（`Enter command: <target>|all …`、`Parse error`、行の途中から始まる謎の `command not found`）。
- 外部コマンドはすべて `< /dev/null`、ffmpeg は `-nostdin` で標準入力を切る。Python の `subprocess.run` でも `stdin=subprocess.DEVNULL` を付ける。

### 8-4. スクリプトの修正がドライブに届かない（旧 S-01）

```text
① PC のプロジェクトフォルダ   …\最終課題_案A_ダンス模倣\pai_final\scripts\   ← 手元で編集する場所
② Google ドライブ             マイドライブ\pai_final\scripts\ ＝ Colab では /content/drive/MyDrive/pai_final/scripts/
```

- Colab が実行するのは**②だけ**。①で直しても②へコピーしなければ古いまま動き、エラーも出ないので最も気づきにくい。読み込んだ後はモジュールのキャッシュで古い版が使われることもある。
- 対策：①で修正 → ②へ上書き → **ノートブックの冒頭で修正版にしかない文字列を `grep` し、古ければ止める**（NB4・NB5 で実装）→ 実行。

```bash
grep -q "z_prev" $P/scripts/render_policy.py || { echo "[stop] render_policy.py が古い版です"; exit 1; }
md5sum /content/drive/MyDrive/pai_final/scripts/*.py   # PC 側の値と比べる
```

- 修正前の版はファイル名を変えて残す（`*_before_*_日付.py.bak`）。結果のファイルの作成時刻とスクリプトの修正時刻を比べ、**どの版のコードで出した結果か**を必ず確かめる。
- 逆向きにも起きる：Colab からノートブックを保存すると、手元で直した版が Colab の版で上書きされる（10/19 に 2 回）。手元で直したら、Colab のタブは保存せずに閉じて開き直す。

### 8-5. 画面が止まったときの操作の使い分け（旧 S-02）

| 操作 | 止まるもの | 残るもの | 使う場面 |
|---|---|---|---|
| **実行を中断** | 動いているセルだけ | 変数、ファイル、仮想環境、切り離した学習 | 長すぎる表示、間違えて実行したセル |
| **セッションを再起動** | Python のカーネル（変数が消える） | `/content` のファイル・仮想環境・チェックポイント、ドライブ、切り離した学習 | 中断が効かない、メモリを解放したい、モジュールを読み直したい |
| **接続解除して削除** | 仮想マシンごと | **ドライブだけ** | 作業の終わり（CU の節約） |

- 判断の順番：まず中断 → 効かなければ再起動（インストールのやり直しは不要。**設定のセル 1 から実行し直す**。学習は止まっていないので監視セルを実行し直せば続きから見られる）→ 接続解除は最後の手段（直前に同期が済んでいるかを確かめる）。
- 大きい動画を `show()`（base64 でノートブックに埋め込む）で表示するとブラウザが固まることがある（比較動画 57 MB）。大きい動画はドライブから直接開く。
- **教訓**：「止める」操作は、何が消えて何が残るかで選ぶ。仮想環境は `/content`、成果物はドライブ、学習は切り離したプロセス、という設計なら、再起動はほとんど何も壊さない。

### 8-6. 動画が作られず、後ろのセルが止まる（旧 4-3）

- 1 ステップ目で終了すると、評価のループはフレームを 1 枚も貯めずに抜け、mp4 は書き出されない（JSON には動画のパスだけが書かれる）【確認済み】。後ろの表示セルが存在しない動画を開こうとして止まった【報告】。
- 対策：①転倒したら終了条件なしの全編動画（`_noterm.mp4`）も書き出す（「止まった時点で止まる正式な評価」と「最後まで見せる動画」を分ける）。②表示セルは動画がなければ表示しない。③評価の表に止まった条件（`fall_reason`）を出す。
- `_noterm.mp4` はお手本から大きくずれても止まらないので、**評価の合否には使わない**。

### 9-1. 学習曲線と「3 つの段階」【実測：A100、4,096 環境、5,000 反復】

| 反復 | 平均エピソード長 | 平均報酬 | `ee_body_pos` 終了 | 関節誤差の指標 |
|---|---|---|---|---|
| 0 | 8 | −0.9 | 868 | 1.90 |
| 300 | 57 | 2.0 | 81 | 2.18 |
| 500 | 182 | 6.7 | 13 | 1.97 |
| 1,000 | 463 | 24.8 | 1.5 | 1.28 |
| 2,000 | 460 | 28.3 | 0.7 | 1.03 |
| 4,999 | **500** | **35.4** | **0.04** | **0.85** |

1. **〜300 反復：立てない**（終了の大半は手足の高さのずれ）。2. **500〜1,000 反復：転ばなくなる**（エピソード長 182 → 463）。3. **1,000 反復〜：精度を磨く**（エピソード長はほぼ上限のまま、関節誤差が下がり続ける）。

- 打ち切りの判断：エピソード長が上限に達しても、誤差が下がり続けている間は続ける。
- 学習の終盤の重点区間は約 6 秒目（全編の約 66 秒）で、物理チェックが hover・slip・自己干渉・可動域外の重なりを予想した秒と一致した（全編でも同じ 66 秒が難所として現れた。4-3）。
- 精度【実測：修正後の正式な評価、4-5】：関節 0.128 rad（約 7.3°）、位置 7.5 cm、最大 16.9 cm。全編の方策をこの区間で測ると位置 5.9 cm・関節 0.170 rad で、20 秒専用のほうが関節は細かかった（3-2）。

| 可動域外 | **0** | 5 |
| 自己干渉 | 86 | 91 |
| 接地中の足滑り 平均 | **0.121 m/s** | 0.147 m/s |

採用した方法は空中で止まる不自然なフレームを約 3 割減らした一方、動きのキレを残すぶん slip と可動域外が少し増えた（2-3）。

### 9-3. 物理チェックの数字は「警告」であり「判定」ではない

- 初期の全編のお手本は 68%（2,842 / 4,196）が hover と判定されたのに、20 秒版は転ばずに学習できた。当時は「足が 2.5〜5 cm 浮いていて hover が水増しされている」と仮説を立てた。
- 全編では、このうち終盤の約 20 cm の浮きが本物の欠陥だった（2-4）。接地の判定を 25 cm に広げると hover は 70 に減った。**指標の値そのものより、どの区間に偏っているかと、学習の重点区間・誤差の大きい区間と重なるかを見る**。

### 9-4. 音源の構成と時間合わせ・権利

- 踊ってみた動画の音源は「イントロ〜1 番サビ後（80.4 秒）」と「ラスサビ〜アウトロ（50.1 秒）」をつないだ短縮版で、継ぎ目は **86.99 秒**。冒頭 6.6 秒は待機、末尾 2.8 秒は余韻【実測：音声の照合】。提出動画の TWICE 公式のワイプは、この継ぎ目に合わせて公式動画を切り貼りしている（`make_submission.sh`）。
- 20 秒版の比較動画では、左（人のメッシュ）と音声を `START=59.815` 秒からずらす。お手本 20.97 秒・物理 20.92 秒（物理側が 1 フレーム短いのは仕様どおり）。
- 権利：楽曲と公式の振付動画を含む動画は、YouTube の著作権の自動判定にかかる可能性がある。まず限定公開で上げて警告を確認してから公開設定を決める。SMPL / SMPL-X と GVHMR の学習済みモデルは GitHub に入れない。

### 9-5. 予備実験の反省

- **評価コードを確かめる前に本番規模の学習を回した**ため、0.02 秒の誤判定（4-6）の解釈で遠回りした。小さな学習（数百反復）で**評価まで一周してから**本番に入るべきだった。
- ライブラリの版を固定せずに始めたため、インストールで止まった（7-4）。

## 10. 新しい振付・ロボットでやり直すときの手順

今回の経験から、同じパイプラインを別の動画で使うときの順番をまとめる。

1. **入力をそろえる**：動画を 30fps ちょうどに変換（2-1）。全編に 1 回だけ推定し、部分はそこから切り出す（2-2）。
2. **環境を固定する**：リポジトリのコミットと pip の版の 2 段階（1-4、7-4）。インストールのセルは冪等に（7-5）。
3. **お手本を物理チェックする**：hover・slip・自己干渉・可動域。腰の高さの推移と足の高さを全編で見る（浮きは 2-4、しゃがみは 2-5 の方法で直す）。
4. **短い区間で、学習から評価・動画まで一周する**（9-5）。評価スクリプトは「終了条件あり／なし」の両方で動かし、学習ログと食い違わないかを見る（4-6）。
5. **全編をゼロから学習する**：「転ばない＋そこそこの精度」（全編で約 6,000〜20,000 反復）で切り上げる（6-5）。
6. **誤差の大きい区間を診断する**：1 秒ごとの誤差、適応サンプリングの重点区間の**分布**（3-6）、物理チェックを並べる。関節は合っていて位置だけずれるなら、お手本の基準を疑う（2-4）。
7. **お手本を直して追加学習する**：同じお手本の上で「旧方策 × 新お手本」の 1 行を入れて効果を切り分ける（4-2）。報酬の許容幅は追加学習のときに段階的に締める（3-5）。
8. **頑健性を確かめてから提出用を選ぶ**：摩擦を 0.5〜1.2 で振り、境界の条件は数回繰り返す（4-8b）。精度・最大誤差・区間別・頑健性を表で並べ、1 つの指標だけで選ばない（4-8c）。
9. **転んだときの進め方**：止まった時刻ではなく崩れ始めの時刻を見る（4-8）→ その秒を物理チェックの 1 秒ごとの表で見る → 重点区間と照らし合わせる → 直した区間で確かめてから全編へ。
10. **動画は残像あり（比較用）と残像なし（提出用）の両方を作る**（`--no-ghost`）。全編の動画は 1 本ずつ書き出す（7-2）。

## 付録 C：用語

| 用語 | 意味 |
|---|---|
| お手本（参照モーション） | ロボットが真似する目標の動き（CSV / npz） |
| エピソード | 1 回の試行。最大 10 秒。転倒（終了条件）で途中終了 |
| 適応サンプリング | 失敗の多い 1 秒区間から優先して試行を始める仕組み（BeyondMimic） |
| 追加学習（ファインチューニング） | 学習済みの重みなどを引き継いで、条件を変えて学習を続けること |
| 価値関数（critic） | 状態の良さを見積もるネット。PPO の学習信号の基準 |
| 行動の std（探索の幅） | 方策が行動に加えるばらつき。学習が進むと縮む |
| 許容幅（std） | 報酬 exp(−誤差² / std²) の幅。小さいほど厳しい |
| ドリフト | お手本に対する立ち位置の水平方向のずれ |
| azimuth / elevation | MuJoCo のカメラが向いている水平角と仰角 |
| hover / slip | 物理チェックの指標。浮いたまま上向きの力が必要 / 接地中に摩擦の限界を超える横の力が必要 |
| CU | Colab のコンピューティングユニット（A100 ≒ 13 CU/時、T4 ≒ 2 CU/時） |
| 終了条件 | 胴体の高さ・手足の高さ・胴体の傾きがお手本から一定以上ずれたら「転倒」とみなして試行を終える仕組み（しきい値 0.25 m など） |
| アンカー | 誤差を測る基準の体の部位（G1 では `torso_link`） |
| `body_pos_relative_w` | お手本の各部位の位置を、ロボットの胴体の水平位置と向きに合わせ直した値。終了判定と報酬の比較対象 |
| ゼロ位相フィルタ | 前向きと後ろ向きに 2 回かけて、時間の遅れを 0 にした平滑化 |
| 逆動力学 | 「この動きをするには外からどんな力が必要か」を計算すること（物理チェック） |
| ハイメモリ（High-RAM） | CPU 側の RAM を増やしたランタイム。GPU のメモリは増えない |
| `--override`（uv） | 依存ライブラリの版の要求を無視して、指定した版に強制的にそろえる指定 |
| 冪等 | 何回実行しても同じ状態になること（インストールのセルの設計方針） |
